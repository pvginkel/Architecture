# Plan 1 — Foundation: real manifest + ArchiMate model

**Read first:** [`00-overview.md`](00-overview.md) and the `project_viewer-rework`
auto-memory. This plan stands alone but assumes the data/schema contract and
locked decisions documented there.

**Goal:** replace the static `viewer/src/data/architecture.ts` taxonomy with a
view-model derived from the real ArchiMate manifest (`/data/v0.1/architecture.json`),
loaded via `?src=`. Apply the ArchiMate-layer colour scheme and the two-icon
node. Generate a vocab module from the schema and type the presentation theme
against it so `tsc` enforces completeness. Leave a working viewer with a minimal
(stopgap) control set — the real filter rail is Plan 3, views are Plan 4.

**Prerequisites:** none. (Independent of Plan 2's logo widening — the viewer
already reads `element.logo` regardless.)

**No scope creep:** do not build the two-panel rail, the per-group search/scroll,
or views here. Keep the existing single control strip, rewired to the new model.

---

## Step 1 — Generator emits `viewer/src/generated/vocab.ts`

Extend `tooling/generate.py` with an `emit_vocab_ts()` that writes a generated TS
module. Wire it into `main()` so `--check` covers its drift (CI gates on a clean
diff).

**Caveat:** `generate.py`'s orphan sweep deletes anything in `GENERATED_DIR`
(`schema/v0.1/generated/`) it didn't emit. `vocab.ts` goes to
`viewer/src/generated/` — a *different* directory — so write it via a separate
path, **not** through the `new_files`/orphan machinery that targets
`GENERATED_DIR`. Add it to the `--check` comparison explicitly.

Emit (all `as const`, with exported union types derived via `typeof`):

- `ELEMENT_KINDS` — the 11 kind names from `subset["kinds"]` (insertion order).
  Plus `ElementKind` union.
- `KIND_TO_ARRAY` — kind name → manifest array key (mirror of
  `ARRAY_TO_ARCHIMATE` inverted to the YAML array names in
  `collect.py:ELEMENT_KIND_ARRAYS`). The viewer reads the JSON arrays through
  this.
- `KIND_TO_LAYER` — kind → `subset["kinds"][k]["layer"]`. Plus `LayerId` union
  (`technology | application | strategy | business | cross-cutting`).
- `RELATIONSHIP_TYPES` — the 13 names (use the same set the relations schema is
  built from: `xsd_relationship_types`). Plus `RelationshipType` union.
- `CAPABILITY_IDS` + `CAPABILITY_LABELS` + `CAPABILITY_SUMMARIES` from
  `schema/v0.1/enums/capabilities.yaml` (`id`/`label`/`summary`). Plus
  `CapabilityId` union.
- `LIFECYCLE_STATES`, `ENVIRONMENTS` (+ labels) from their enum files.
- Human-readable display labels: `KIND_LABELS`, `RELATIONSHIP_LABELS`,
  `LAYER_LABELS`. Subset kinds/relations have no `label` field — humanise the
  PascalCase/Name (e.g. `ApplicationComponent` → "Application Component",
  `runs-on`-style not applicable here). A small `humanise()` in the generator is
  fine; if a hand-authored label is later wanted, add `label:` to `subset.yaml`
  and read it.

Header the file `// GENERATED by tooling/generate.py — do not edit`. Keep output
deterministic (sorted where order isn't semantic; preserve subset insertion
order where it is).

Verify: `cd tooling && poetry run python generate.py` writes the file;
`poetry run python generate.py --check` is clean. **Commit.**

## Step 2 — Manifest types + loader

New `viewer/src/data/manifest.ts`:

- TypeScript interfaces mirroring the data contract (element kinds, relation,
  `derived`, top-level). Element type is a single `ArchElement` with the union of
  optional per-kind attributes (`environment?`, `cluster?`, `stereotype?`,
  `logo?`, `homepage?`, `sourceRepository?`, `stats?`) — the JSON is loose enough
  that one interface + the kind tag is simplest.
- `resolveSrc(): string` — read `?src=` from `location.search`; default to
  `${import.meta.env.BASE_URL}../data/v0.1/architecture.json` (the manifest is
  served at `/data/v0.1/` while the viewer is at `/viewer/`; confirm the relative
  path resolves against the deployed base, otherwise hardcode `/data/v0.1/…`).
- `async loadManifest(src): Promise<Manifest>` — `fetch` + `res.json()`. **No
  try/catch swallowing** — let a failed fetch / bad JSON throw; surface it as a
  visible error state in the app shell (a plain error panel), not a silent empty
  canvas.

**Local dev:** the production manifest is built by the pipeline into the image;
in dev there's no `/data/` server. Provide a committed sample at
`viewer/public/sample-architecture.json` (copy
`tooling/tests/fixtures/happy-path/expected-dist/architecture.json`, or a richer
hand-made one) and default `?src` to it when running under `vite dev`. Keep the
prod default pointing at the served manifest.

## Step 3 — View-model: manifest → ReactFlow

New `viewer/src/data/model.ts` (replaces the role of the old `architecture.ts`):

- Flatten the 11 arrays into `ArchElement[]`, tagging each with its `kind` (via
  `KIND_TO_ARRAY` inverse) and computed `layer` (`KIND_TO_LAYER`).
- Build `elementCapability: Map<elementId, CapabilityId>` by inverting
  `manifest.derived.capabilityRealizations`. (If an element realizes more than
  one capability, pick the first deterministically; capability is only used for
  the right-icon fallback.)
- `toFlowNodes(elements)` / `toFlowEdges(relations)`: mirror today's
  `toFlowNode`/`toFlowEdge` in `ArchitectureMap.tsx` but sourced from the new
  element/relation shape. Node `data` carries: id, label, kind, layer,
  capabilityId?, producer, environment?, logo?, summary, lifecycle, stats.
- Keep `viewer/src/components/layout.ts` (ELK layered) as-is; it filters on
  `node.type === "architecture"`. Node dimensions can stay `270×132`.

Delete `viewer/src/data/architecture.ts` once `ArchitectureMap.tsx` no longer
imports it.

## Step 4 — Presentation theme (typed against vocab)

New `viewer/src/theme.ts`:

```ts
import type { ElementKind, LayerId, CapabilityId } from "./generated/vocab";
import type { LucideIcon } from "lucide-react";

export const LAYER_ACCENT: Record<LayerId, string> = { … };   // miss one → tsc error
export const KIND_ICON: Record<ElementKind, LucideIcon> = { … };
export const CAPABILITY_ICON: Record<CapabilityId, LucideIcon> = { … };
```

- `LAYER_ACCENT` — the theme-adapted ArchiMate hues (overview starting values;
  tune for legibility on `--panel #fbfbf8`). The node card already lightens an
  accent via `color-mix` (`architecture.css:273`) — feed the layer accent into
  the existing `--node-accent` mechanism.
- `KIND_ICON` — best-effort Lucide match per kind. Suggested starting set
  (keep the look of today's icons): Node→`Server`, Device→`HardDrive`/`Cpu`,
  SystemSoftware→`Boxes`, ApplicationComponent→`Box`/`AppWindow`,
  ApplicationService→`Workflow`, ApplicationInterface→`Plug`,
  TechnologyService→`Cog`/`Cable`, TechnologyInterface→`Plug`,
  Capability→`Sparkles`/`Target`, BusinessService→`Briefcase`,
  Grouping→`Group`. Refine to taste.
- `CAPABILITY_ICON` — generic icon per capability id, used only as the
  right-image fallback when no `logo`. Reuse today's mapping spirit
  (`ArchitectureMap.tsx:122`).

**Completeness:** because these are `Record<Union, …>`, `tsc` fails on a missing
kind/layer/capability and on a stale key not in the union. That is the guard —
don't add a runtime "default icon" path.

## Step 5 — Two-icon node + loud runtime placeholder

Rework `ArchitectureNodeCard` in `ArchitectureMap.tsx`:

- **Left:** `KIND_ICON[kind]` (Lucide glyph).
- **Right:** `<img>` of `${BASE_URL}logos/${logo}` if `logo` set; else the
  `CAPABILITY_ICON[capabilityId]` Lucide glyph if the node realizes a capability;
  else nothing. Keep the existing `arch-node__top` / `arch-node__icon` /
  `arch-node__logo` structure.
- Accent = `LAYER_ACCENT[layer]` via `--node-accent`.
- Meta line: show producer + `stats.introduced`/version etc. as today.
- **Runtime skew:** if `kind`, `layer`, or a referenced `capabilityId` is absent
  from the vocab/theme maps (data newer than build), render a glaring placeholder
  badge and `console.error("[viewer] unknown <thing> '<value>' — vocab is stale,
  rebuild")`. Loud, non-crashing. (Per fail-fast: do not substitute a generic
  icon silently.)

Node status classes today key off `data.status` (old taxonomy). Replace with
`lifecycle` (`active`/`deprecated`/`removed`) styling, or drop the status accent
entirely for now.

## Step 6 — Rewire the stopgap controls

The current `.controls-panel` (search + capability/relationship toggles,
`ArchitectureMap.tsx:714`) references the old vocab. Rewire it minimally so the
viewer is usable until Plan 3:

- Search box (label/kind/summary/producer haystack).
- Toggle groups for **Layer** (5) and **Element kind** (11) and **Relationship
  type** (13), built from the vocab. Within-group OR, across-group AND; relations
  default to all-among-visible.
- Default the dataset to **prd + no-environment** elements (drop dev/tst/uat) so
  the canvas isn't 4× multiplied — even though the Environment filter UI lands in
  Plan 3, apply the prd default now.
- Keep "Reset Filters".

This whole strip is replaced in Plan 3; keep it simple.

## Step 7 — Wire it together

- `ArchitectureMapInner`: load manifest (Step 2), build model (Step 3), feed the
  visible-graph memo, render. Handle loading + error states in the shell.
- Keep the `parent-bridge` channel; the `view-change` payload can stay a generic
  JSON string of the current filter state.

## Acceptance criteria

- `cd tooling && poetry run python generate.py --check` clean; `vocab.ts` present
  and committed.
- `cd viewer && npm run build` (`tsc --noEmit && vite build`) passes — a missing
  theme entry must fail `tsc`.
- `npm run dev` renders the sample manifest: nodes coloured by ArchiMate layer,
  kind glyph left + logo/capability-fallback right, ELK layout, working
  search + layer/kind/relation toggles, prd-only by default.
- Removing a `LAYER_ACCENT`/`KIND_ICON` entry breaks the build (guard proven).
- An injected unknown kind/capability in the sample renders the loud placeholder
  + console error rather than crashing or silently defaulting.
